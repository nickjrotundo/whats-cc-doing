ccdoing (What's CC Doing) - Privacy Policy

Effective 2026-08-31. Applies to the ccdoing Claude Code plugin and the whats-cc-doing Python package.

The short version

ccdoing runs entirely on your machine. It has no telemetry, no analytics, no accounts, and it never sends anything to the developer. Data leaves your machine only through channels you explicitly configure (notifications) or actions you take yourself (publishing a page).

What it reads, locally

  • Git metadata of the monitored project (commit times, short log lines).
  • The process table, to check whether configured processes are running. Rendered process lines are redacted by default (process name and argument count, not full command lines).
  • File modification times for globs you configure, and the contents of log or results files you point signals at.
  • Health endpoints (HTTP status of URLs you configure, e.g. localhost:8500/health).
  • Structural metadata of Claude Code's on-disk session files: event timestamps, event types, working directories, session and subagent identifiers, user-set session names, and subagent labels. Conversation content is never read out, rendered, stored, or transmitted.

What it writes, locally

A status page (status.html) and machine snapshot (status.json) inside the monitored project, watchdog state under .ccdoing/, and a small registry of monitored project paths under your XDG state directory. All local files you can inspect and delete at any time.

What can leave your machine, and only if you set it up

  • Notifications. If you configure a notification target (ntfy, Slack, or any apprise-supported service), escalation messages are sent there. They contain the project name, the verdict, and short signal summaries. For ntfy.sh, anyone who knows your topic name can read the topic - ccdoing stores it in a gitignored file and treats it as a secret; you should too.
  • The optional nudge. The opt-in tier-3 action delivers one informational message to another Claude Code session on the same machine, over a local socket. It does not leave the machine. The message text is a file you approved beforehand plus signal readings.
  • Serving. ccdoing serve binds 127.0.0.1 by default. Binding other interfaces, or publishing a status page anywhere, is your action; remember the page shows project names, session names, and file names.

What the developer receives

Nothing. There is no phone-home of any kind. If you file a GitHub issue, that is governed by GitHub's terms, not this policy.
